# ezPLM 原型 V5.2 · 双版本（客户确认版 / 内部演示版）

在 V3→V4 基础上，依据 GPT 第三方诊断逐项修复运行时缺陷与业务一致性问题。
严格遵循《AI 驱动供应链智能协同系统开发合同》附件一 Phase 1 范围；未新增业务模块、未扩大范围。

- `check-v5_1.py` / `check-v5.py` / `check-v4.py` — 历次校验脚本，保留以便回溯

## V5 本轮（基于 GPT 诊断）修复要点
**两个 P0（运行时）**
1. CSV 导出 TypeError：`ezExportCSV` 兼容两参 `(name,table)` 与三参 `(name,headers,rows)`，加防御校验与 `.csv` 后缀；Node 实测 25 个调用点 0 异常。
2. Tab 失效（ar-ap/procurement/trace）：处理器兼容 `.pane`/`.tab-pane`，按 `id||data-pane` 匹配；补 `.pane` CSS；jsdom 实测 8 次切换均正确。

**业务一致性 / 主体**
3. 系统使用方 = 乾创电子（登录用户、Dashboard、OPO/Call 料邮件落款）；联创科技保留为下游客户样例。
4. 报价：静态值改 `—` 由 recalc 填充；毛利率改用透明成本基线（物料+加工，口径待甲方确认），删除无依据的 0.82；C 模式去掉未实现的"工程费另计"。
5. 物料报价 GTB 真正纳入 MOQ + SPQ（损耗率参数待客户确认，默认 0）；新增 MOQ/SPQ 列。
6. 物料报价逐项确认闭环：每条异常落 `decision/decisionNote/confirmedBy/confirmedAt`，全部给出结论才可提交审批。
7. 物料报价 Stepper 完成态全部置 done。
8. 计划辅助：新增工艺路线 `route`/当前工序 `currentOp`，未齐料工单不进入上线队列；`fixHours` 真正读取输入、写回 WOS、重算工时与排产与 KPI。
9. OPO `simulateReply`：KPI（含异常 8→10）、差异表、异常清单同步更新；`portalSubmit` 真正更新行状态。
10. 交付页培训方式改"远程为主、现场另计"，去除固定"半天"；"下载全部模板"真正逐个下载；"主管"对齐为"管理人员（主管）"。

## V5.2 本轮（GPT 第三轮诊断 · 状态冻结与行级一致性）修复要点
1. **报价审批后冻结（P0）**：提交时保存不可变 submittedSnapshot、审批通过保存 approvedSnapshot；PENDING/APPROVED 状态下客户类别、折扣、分类修正、导入 BOM 全部冻结；PDF 与导出一律使用快照值，改动实时输入不再影响已批准报价。需修改须「创建修订版」回到草稿（版本号 +1），原快照保留备查。
2. **单产线排产无重叠 + 16h/天（P0）**：游标改为完整 DateTime；新增两班工作日历（08:00–24:00=16h）推进函数；下一工单开始 = max(上一完成, 物料齐料, 工序就绪)，不再重叠。
3. 报价退回后不再死路：退回记录原因，提供「创建修订版」恢复草稿并可重新提交。
4. 物料报价新价/新供应商输入框始终渲染，选 REQUOTE/换货源即时启用（不再需先保存失败）。
5. PM 确认覆盖全部「原始异常行」（wasFlagged 集合），重新询价/换货源成功后仍记录 confirmedBy。
6. 流程状态文案改用「未处理数」而非「当前超线数」。
7. 「更换货源」记录新供应商与 Lead Time。
8. 工序真正参与排产：completedOps 按比例扣减排产工时（已验证 29.7h→19.8h）。
9. OPO 改为**行级统一状态模型 opoLines[]**：KPI、未回复供应商表、交期差异表、异常清单、门户行全部由行级数据派生；门户提交后该行据回复结果自动从异常清单移除，三表与 KPI 全程一致。
10. check-v5_2.py 新增 §33–§38 **jsdom 运行时行为断言**，直接验证上述 P0/P1 的真实运行结果（而非仅源码关键词）。

## V5.1 本轮（业务状态机加固）修复要点
1. 报价状态机：DRAFT→PENDING_APPROVAL→APPROVED/REJECTED；分类未全部人工确认不得提交；PDF/正式报价单仅 APPROVED 后可用；不可重复提交。
2. 物料报价重新询价闭环：异常默认无结论（须逐项人工选择）；REQUOTE/换货源/调价须采购填新价并重新校验通过；采购处理→PM 确认→管理人员审批角色分离。
3. 计划排产：引入计划基准日 + 齐料日期比较；所有工单（含未来齐料）均有顺位与建议开始/完成时间；工序进度字段参与展示与判定。
4. OPO 统一状态模型：所有 KPI、未回复供应商表、脚注由单一 OPO 状态对象经 renderOpo() 渲染；门户提交防重复；未回复 KPI 恒等于供应商表合计。
5. 角色：移除范围外"品质"角色（→ 采购/管理人员）。
6. 可达性：supplier.html 通过 OPO 门户页入口可达，消除孤立页。
7. 文案：报价规则区标注"原型示例，最终以甲方确认规则表为准"；"下载全部模板"提示多文件下载可能被浏览器拦截。

## 静态原型边界（重要）
当前为静态高保真原型，用于确认页面、字段、流程与范围；不代表后端、接口、邮件与文件生成已全部完成。
- AI 输出仅辅助人工判断，须授权人员确认后生效，支持人工修正并留痕。
- ERP/MES 集成方式（API/中间表/视图/Excel/RPA）与联调状态待客户 IT 确认；接口不可用时走替代路径。
- 导出按钮原型导出 CSV；正式系统按双方确认模板生成 XLSX/PDF。邮件/连接测试均为原型模拟。

## 运行
- 打开原型：浏览器打开 `customer-confirmation/index.html` 或 `internal-demo/index.html`。
- 校验：`python3 check-v5_2.py`（需 Python 3；装有 Node.js + jsdom 时会运行 §33–§38 的**无头 DOM 行为断言**：报价审批后参数冻结/快照不漂移、退回后可修订重提、单产线排产无重叠且 16h/天跨天正确、completedOps 真正影响排产、OPO 三表与 KPI 由行级数据一致、物料报价新价输入即时显示且全部原始异常获 PM 确认）。jsdom 行为断言比纯关键词检查更接近真实运行，但仍不等于真实浏览器；正式交付前建议用 Playwright/Cypress 复验关键流程。
